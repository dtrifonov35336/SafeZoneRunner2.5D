# SAFE ZONE RUNNER — ПАМЯТКА ПРОЕКТА

Дата обновления: 30.08.2026

## 1. Общая идея игры

Жанр:
- мобильный 2D endless runner / survival runner;
- Android как основная платформа;
- дальнейшая публикация в RuStore и Яндекс Играх;
- игра создаётся одним человеком без команды;
- разработчик не программист и не художник, поэтому разработка ведётся максимально доступными средствами, своими руками и с помощью нейросетей.

Основная концепция:
Игрок выбирает персонажа и участвует в бесконечной гонке за выживание, спасаясь от монстров/зомби.

Сюжет первого забега:
- произошла внезапная катастрофа;
- военные эвакуируют огромное количество людей;
- образовался длинный поток/вереница выживших;
- люди движутся от города к безопасному месту;
- игрок всё время находится в самом конце толпы;
- игрок первым замечает приближающихся монстров;
- военные начинают подгонять людей;
- толпа ускоряется и переходит на бег;
- задача игрока — пробраться из конца толпы к её началу, затем попасть в убежище;
- позади монстры/зомби убивают тех, кто не успевает;
- в убежище/ангаре игрок и спасшиеся получают передышку;
- это не конец игры, а конец одного раунда;
- после короткой подготовки начинается следующий раунд.

Будущие идеи:
- несколько убежищ, между которыми игрок может выбирать;
- ситуации вроде «спаси ребёнка», «помоги старушке» и другие мини-испытания;
- разные типы окружения;
- более сложная и живая толпа;
- разные типы монстров;
- мета-прогресс между раундами.

## 2. Визуальный стиль

Игра:
- 2D;
- мобильный runner;
- вертикальная ориентация телефона;
- вид сверху / top-down, близкий к мобильным runner-играм;
- дорога является основным фоном/игровой поверхностью;
- сцена должна визуально восприниматься как непрерывная дорога;
- при переходе между кусками сцены цветовая гамма должна совпадать;
- меняется обстановка, но не общий цветовой тон мира.

Первый раунд:
- окраина разрушенного города;
- дорога ведёт от города к безопасной зоне;
- вокруг дороги разрушения, мусор, машины, баррикады и элементы недавней катастрофы;
- надписи «Безопасная зона», «Убежище» и подобные должны находиться на плакатах, баннерах или ткани;
- никаких современных капитальных указателей, которые выглядели бы так, будто были установлены давно: апокалипсис произошёл внезапно и недавно.

Важное решение:
- людей из фоновой картинки дороги убрали;
- люди/толпа должны быть отдельными игровыми объектами;
- фон состоит из дороги и окружения;
- под баннером безопасной зоны должен быть свободный проход.

Созданы/обсуждались изображения:
1. Первый кусок дороги — начало эвакуационного маршрута.
2. Второй кусок дороги — продолжение маршрута; цвет должен совпадать с первым.
3. Главный персонаж — спрайт для использования в игре, в дальнейшем нужен полноценный набор кадров анимации.
4. Персонаж должен быть ориентирован под top-down runner.

## 3. Unity — текущий проект

Движок:
- Unity;
- 2D проект;
- используется Input System package;
- целевая платформа Android;
- экран Portrait / вертикальный.

Структура папок проекта:
- Assets/Scenes
- Assets/Sprites
- Assets/Prefabs
- Assets/Scripts
- Assets/Animations
- Assets/Audio
- Assets/UI

Основная сцена:
- MainRoad

Камера:
- Main Camera;
- Projection = Orthographic;
- Transform примерно X=0, Y=0, Z=-10;
- Rotation = 0,0,0;
- Orthographic Size был настроен примерно на 7 как стартовая точка;
- Game view настроен на вертикальный формат;
- Android Default Orientation = Portrait.

Важно:
- поворот камеры по Z не используется для получения вертикального Game view;
- вертикальность задаётся через Aspect/Portrait в Game view и Portrait в Player Settings.

## 4. Игрок

Корневой объект:
- Player

На Player:
- Rigidbody2D;
- Collider2D;
- PlayerMovement2D;
- физика не должна влиять на визуальную анимацию.

Для Rigidbody2D:
- Gravity Scale = 0;
- Freeze Rotation Z включён.

Предпочтительная архитектура:
Player
└── Visual

Player:
- отвечает за физику;
- движение;
- ограничения по дороге;
- будущие столкновения.

Visual:
- отвечает за Sprite Renderer;
- Animator;
- визуальную анимацию.

## 5. Движение игрока

Игрок в runner-механике не должен физически бежать вперёд по миру.
Вместо этого:
- игрок остаётся примерно в нижней части экрана;
- дорога/окружение движутся вниз;
- игрок управляется по горизонтали.

Используется Input System.

Актуальная логика PlayerMovement2D:
- движение A/D или стрелками ←/→ для теста на ПК;
- горизонтальная скорость sideSpeed;
- ограничение X между leftLimit и rightLimit;
- вертикальное движение самого Player не используется в текущей версии.

Важная ошибка, которая уже встречалась:
InvalidOperationException:
"You are trying to read Input using the UnityEngine.Input class, but you have switched active Input handling to Input System package in Player Settings."

Причина:
- проект использует новый Input System;
- старый Input.GetAxisRaw нельзя использовать при текущей настройке.

Исправление:
- код переведён на UnityEngine.InputSystem;
- для теста используется Keyboard.current.

## 6. Бесконечная дорога

Дорога состоит минимум из двух одинаковых по высоте кусков:
- Road_1
- Road_2

Их движение:
- оба двигаются вниз;
- когда один кусок уходит достаточно низко, он перемещается выше второго;
- получается бесконечная прокрутка.

Скрипт:
- RoadScroller

Ключевое исправление:
Изначально использовалась вручную заданная roadHeight = 20.
Это давало большой разрыв между кусками дороги.

Исправлено:
- фактическая высота берётся из SpriteRenderer:
  roadHeight = road1.GetComponent<SpriteRenderer>().bounds.size.y;

После этого разрыв исчез и дорога работает нормально.

Важно:
- отдельный фон не нужен;
- дорога сама является основной поверхностью/фоном;
- проблема «синий экран между картинками» возникала из-за пустого пространства между дорожными спрайтами.

## 7. Анимация игрока

Нужно подготовить анимацию заранее, чтобы позже просто заменить спрайты.

Создана идея:
- Player/Visual;
- Animator;
- Animation Clip;
- фейковая анимация через изменение Position/Rotation/Scale;
- цель — добавить визуальную «живость», пока нет готового набора кадров.

План:
- Player_Idle
- Player_Run

Для runner-версии:
- Run должен быть основной анимацией, так как игрок почти всегда бежит.

Для настоящей анимации:
Есть два спрайта:
1. персонаж с левой ногой в шаге;
2. персонаж с правой ногой в шаге.

Их нужно собрать в цикл:
- кадр 1 — левая нога;
- кадр 2 — правая нога;
- снова кадр 1;
- включить Loop Time.

Animator:
- лучше держать на Visual;
- позже можно сделать параметр IsRunning и переходы Idle <-> Run;
- пока можно использовать Run как Default State.

Важно:
- физическое движение Player и визуальная анимация Visual — разные вещи;
- Animator не должен двигать корневой Player по миру.

## 9. Ошибка Device Simulator

Встречались ошибки:

NullReferenceException:
UnityEditor.DeviceSimulation.UserInterfaceController.StoreSerializedStates

и

ArgumentException:
"An item with the same key has already been added.
Key: UnityEditor.AdaptivePerformance.Editor.AdaptivePerformanceUIExtension"

Это выглядит как проблема Unity Editor / Device Simulator / Adaptive Performance, а не ошибка игрового скрипта.

Рабочее решение:
- закрыть Device Simulator;
- продолжать тестирование через обычный Game view с Portrait;
- при необходимости позже разобраться с пакетами Device Simulator и Adaptive Performance.

## 10. План разработки игры

Разработка должна идти постепенно.

Этап 1 — базовый runner:
1. Игрок.
2. Движение влево/вправо.
3. Бесконечная дорога.
4. Препятствия.
5. Столкновения.
6. Финиш / безопасная зона.

Этап 2 — ядро концепции:
1. Поток людей.
2. NPC движутся по дороге.
3. Игрок пробирается через толпу.
4. Толпа замедляет/мешает игроку.
5. Зомби/монстры давят сзади.
6. Условие проигрыша.
7. Успешный забег до убежища.

Этап 3 — раунд/метаигра:
1. Ангар/убежище.
2. Передышка.
3. Награда за раунд.
4. Валюта.
5. Снаряжение.
6. Персонажи.
7. Улучшения.
8. Следующий раунд.

Этап 4 — разнообразие:
1. Несколько убежищ.
2. Выбор маршрута.
3. Спасение NPC.
4. Дополнительные испытания.
5. Разные локации.
6. Разные типы врагов.
7. Более сложная толпа.

Этап 5 — монетизация:
1. Rewarded Ads.
2. Внутриигровые покупки.
3. Магазин.
4. Платная валюта.
5. Косметика.
6. Второй шанс после смерти.
7. Наборы.

## 11. Монетизация — обсуждённая модель

Основная модель:
- бесплатная игра;
- реклама;
- внутриигровые покупки.

Публикация:
- RuStore;
- Яндекс Игры.

Желательно:
- один общий Unity-проект;
- отдельный слой/адаптер для монетизации;
- реализация интерфейсов площадок отдельно.

Предварительная экономика:

Бесплатная валюта:
- жетоны;
- выдаются за игру, достижения, ежедневный вход, награды и рекламу.

Премиальная валюта:
- кристаллы;
- покупаются за реальные деньги;
- используются для премиум-предметов, персонажей, косметики, ускорения прогресса, вторых шансов и т.п.

Предварительные цены, которые можно тестировать:
- 59 ₽;
- 149 ₽;
- 299 ₽;
- 599 ₽;
- 999 ₽.

Это НЕ утверждённые цены и НЕ гарантия оптимальной экономики.
Это стартовая гипотеза для тестирования.

Особенно интересный товар:
- «Второй шанс» после смерти;
- вариант: посмотреть рекламу или заплатить премиальной валютой.

Другие возможные точки монетизации:
- ×2 награда за просмотр рекламы;
- бесплатная награда за rewarded ad;
- персонажи;
- косметика;
- экипировка;
- наборы.

Важно:
- не делать pay-to-win основной моделью;
- большая часть контента должна быть доступна через игру;
- платёж должен ускорять/украшать/давать удобство, а не ломать баланс.

## 12. Реалистичные ожидания по доходу

Главный риск — не техническая монетизация, а отсутствие игроков.

Условные сценарии обсуждались только как ориентиры, не как прогноз:
- 1 000–5 000 установок: доход может быть от 0 до небольших сумм;
- 20 000–50 000 установок: возможен заметный дополнительный доход;
- 100 000+ установок: потенциально сотни тысяч рублей при хорошей удерживаемости;
- 500 000–1 000 000+ установок: потенциально серьёзный бизнес-результат.

Важно:
- это не финансовый прогноз;
- фактический доход сильно зависит от retention, DAU/MAU, количества показов рекламы, конверсии в покупку, ARPPU, географии аудитории, условий площадок и качества игры.

Цель первой игры:
- не ставить сразу цель «заработать миллион»;
- сначала добиться первого работающего релиза;
- затем первых 10 000 ₽;
- потом улучшать удержание и экономику.

## 13. Россия, ИП на НПД

У разработчика:
- ИП;
- НПД.

Обсуждалось:
- RuStore позволяет монетизацию для ИП на НПД при соблюдении требований площадки;
- лимит дохода НПД — 2,4 млн ₽ в год;
- ставка НПД зависит от вида дохода: 4% от физлиц и 6% от ИП/организаций;
- при росте дохода выше лимита нужно заранее решать вопрос о другом налоговом режиме;
- перед существенными поступлениями важно отдельно подтвердить свою схему налогообложения и документооборот у ФНС/бухгалтера.

Также обсуждалось:
- у площадок есть собственные комиссии/условия выплат;
- экономику надо считать после комиссий и налогов, а не по цене в магазине.

## 17. Принцип работы со мной

Работа должна вестись максимально пошагово.

Пользователь хочет:
- не общие объяснения;
- а инструкции «нажми сюда → выбери это → введи это → нажми Apply»;
- готовый код;
- объяснение, куда именно вставить код;
- проверку ошибок по логам;
- движение маленькими рабочими шагами.

При продолжении проекта желательно:
1. сначала учитывать эту памятку;
2. не пересобирать уже работающие системы без необходимости;
3. не усложнять архитектуру раньше времени;
4. каждую новую систему сначала делать простой рабочей версией;
5. потом улучшать.

Создать и выпустить первую коммерческую версию мобильной игры в одиночку.
